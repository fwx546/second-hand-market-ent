# 私信与自愿交换联系方式上线

## 已实现的行为

- 商品/服务详情只有私信入口，不向其他登录用户直接展示微信、QQ 或手机号。历史联系接口只允许发布者本人读取。
- 发布不收集联系方式；没有任何号码的双方也能正常私信。
- 对话中任一方均可发起交换。发起者填写一项联系方式并勾选自愿分享；接受者也要选择自己的方式、填写并勾选同意，之后双方才同时看到本次信息。
- 申请 7 天有效，支持撤回和拒绝；已接受后任一方可停止共享。终态不返回号码，清理快照时保留状态元数据。到期清理在之后访问/申请时发生，不依赖定时后台任务。
- 拒绝或停止共享后 24 小时内不能再次申请；每人 24 小时最多 5 次、每对话最多 3 次。不交换不影响私信。
- 联系方式不写入普通消息或会话列表；用户自行输入的消息、公开描述或图片仍可能包含号码，需自行检查。

## 正式数据库操作

代码可以先自动部署：旧库不再向他人提供旧联系方式，私信仍正常，交换卡片显示“暂未开通”。新交换记录只有迁移就绪后才允许创建。

维护者须有对应 Cloudflare/D1 权限，GitHub push 权限不包含数据库权限。本次没有登录或修改正式数据库，也没有复制任何真实联系方式。

1. 确认 `main` 构建部署正常，暂停 API 写入并备份 D1，操作方法沿用 [服务类上线说明](service-listings-rollout.md)。备份仅保存在忽略目录，不发到聊天、日志或 Git。
2. **先检查服务类迁移是否已完成。** 若仍是旧商品分类约束，先按上述指南执行 `cloudflare/migrations/0002_service_listings.sql` 并核对原数据。该文件会重建商品表，必须在任何交换数据产生前完成。
3. 仅当 `contact_exchanges` 表尚不存在时，从仓库根目录执行一次新增表迁移：

   ```powershell
   npx --yes wrangler@4.151.2 d1 execute DB --remote --config cloudflare/wrangler.json --file cloudflare/migrations/0003_contact_exchanges.sql
   ```

   不重跑初始化 `0001_schema.sql`，不盲目执行全部 migrations apply。新文件仅建表、索引及约束，不改现有商品/用户记录。
4. 核对原有表记录未改变，执行 `PRAGMA foreign_key_check`，应无结果；确认新表初始为空。恢复 `JUZI_SITE_ENABLED=true`。
5. 用两个本人控制的测试账号刷新私信页，验证双向申请、拒绝/撤回、接受后双方可见、停止后刷新双方均不可读；再核对未登录/第三个账号无法访问。不把真实号码贴进截图或测试报告。

即使先建了新表，代码也会在旧服务类结构未迁移时禁止创建交换记录，避免之后的商品表重建级联删除交换数据。推荐仍按 0002 → 0003 的顺序操作。既有迁移不修改、不重复执行；已完成的步骤跳过。

本地/历史 Sites 对应 `drizzle/0010_contact_exchanges.sql`，从根目录 `npm run build` 后执行 `npm run db:migrate`，只操作本地模拟数据库。Cloudflare 正式站不要运行历史 Sites 数据导入来代替增量迁移；未来备份应使用包含新表的完整 D1 导出。

## 验证与实际边界

- 自动测试使用虚构双方和第三方，覆盖同意前隐藏号码、身份/Origin/归属校验、号码格式、重放、并发、过期、拒绝/撤回/停止、限流、旧库兼容及迁移后启用。
- 前端与真实业务后端联测覆盖勾选同意、申请、接受、双方查看、停止共享；验证未发送消息不受影响，过时轮询或切换身份不会恢复旧号码。
- 本轮浏览器连接持续超时，尚未完成真实双浏览器全流程、手机视觉和键盘验收。自动化联测不能替代这些检查；正式数据库及真实学校邮箱登录也未在本轮操作。
- 普通私信和交换记录由服务端保存，未声称端到端加密。停止共享不能撤回他人已保存的内容；历史完整备份也可能保留旧快照，应按私密备份管理。
